# Сценарий демонстрации (защита, ~10 минут)

Все игры ниже — из **тестового года 2008**, который модель не видела при обучении. Реальная оценка критиков известна,
поэтому прогноз можно сразу сверить с фактом.

## Перед защитой (за 10 минут)
1. Запустить Docker Desktop, затем в папке проекта:
   ```
   docker compose up -d
   ```
2. Проверить, что всё живо: http://localhost:8000/health → `"llm_available": true`.
3. Открыть вкладки:
   - приложение — http://localhost:8501
   - n8n — http://localhost:5678 (вкладка *Executions* у workflow)
   - почта — Gmail (или Mailpit http://localhost:8025, если SMTP не настроен)
   - Google-таблица с листом `Actions`
   - (по желанию) MLflow — `.venv\Scripts\mlflow ui --backend-store-uri sqlite:///mlflow.db` → http://localhost:5000
4. Один «прогревочный» запуск агента на любой игре — первая генерация после старта чуть медленнее.

## 1. Дашборд (1 мин) — «какую задачу решаем»
- 1212 игр, **22.8 %** получили негативный отзыв (оценка < 60).
- Негативный отзыв стоит денег: медианные продажи у таких игр заметно ниже → это и есть «выручка под риском».
- Блок качества данных: 6 константных признаков-ошибок источника, 21.8 % пропущенных издателей, найденная утечка.

**Сказать:** «Издатель до релиза хочет знать риск провала и что с ним делать — система отвечает на оба вопроса».

## 2. Модели и XAI (1.5 мин) — «почему этой модели можно доверять»
- 4 модели + baseline, выбор по **PR-AUC** на 5-fold CV (классы несбалансированы, важен поиск провалов).
- XGBoost: PR-AUC **0.385** на тесте 2008 против **0.177** у baseline — в ~2 раза лучше.
- Тест — по времени (обучение 2004–2007, тест 2008), как в реальной жизни.
- SHAP: главный фактор — **длина сюжета**, дальше жанр Simulation, сиквел, репутация издателя.

**Сказать про утечку:** продажи, цена б/у и опросы известны только после релиза — исключены; репутация издателя
считается только по прошлым годам.

## 3. Низкий риск → ничего не тратим (1 мин)
*Прогноз и действия → Существующая игра →* **Fallout 3** (PlayStation 3) → «Прогноз».
- Риск **13 %**, уровень «низкий». Реальная оценка — **90**: модель права.
- «Запустить AI-агента» (~15 с): агент изучает игру и фиксирует **только мониторинг**.
- Письмо команде **не уходит** (мониторинг пишется только в журнал / Google Sheets).

**Сказать:** «Даже если LLM предложит потратить деньги на игру с низким риском, бизнес-правило заменит это мониторингом —
это guardrail».

## 4. Высокий риск → меры + человек в контуре (3 мин) — главный сценарий
*Существующая игра →* **Iron Man** (Sony PSP) → «Прогноз».
- Риск **≈ 52 %** (порог 22 %), уровень «высокий». Реальная оценка — **44**: модель поймала провал.
- SHAP-график: какие признаки толкают риск вверх (лицензионная игра, короткий сюжет, PSP…).
- Таблица мер: каждая мера проверена **через модель** (what-if) или по явному допущению; стоимость, выгода, чистая
  ценность, нужна ли согласование.
- Таблица мер: модуль решений рекомендует **QA (60 k$) + перенос релиза (300 k$) + плейтест (25 k$)**.
- «Запустить AI-агента» (~15 с). Показать:
  - отчёт: риск, причины, похожие игры (5 из 5 негативные), история издателя Sega, решение;
  - **трассировку** — какие из 6 инструментов вызвала LLM и с какими аргументами;
  - созданное действие: модель 3B обычно выбирает **расширенное QA (60 k$) → «ожидает согласования»**
    (порог одобрения — 50 k$). Если выберет и плейтест — он запустится сам, и команде уйдёт письмо.
- Переключиться на почту: пришло письмо **«Approval needed»** со ссылками ✅ Approve / ❌ Reject.
- Google-таблица: новая строка `action_created`.

**Сказать честно:** LLM выбирает скромнее модуля решений (см. слайд «Оценка агента»: 42 % от оптимальной выгоды у 3B,
58 % у 7B). Поэтому модуль решений остаётся эталоном и страховкой, а дорогие меры всё равно решает человек.

## 5. Решение менеджера (1.5 мин)
- В письме нажать **Approve** у QA → страница подтверждения API.
  (Или в приложении: *Согласование (HITL)* → «Одобрить»; там же можно «Отклонить» одно из старых тестовых действий,
  чтобы показать вторую ветку.)
- Показать результат:
  - письма команде «Approved by manager: EXTENDED_QA» и/или «Rejected: …»;
  - в таблице строки `action_decided`, кто и что решил;
  - в n8n → *Executions*: путь по ветке Approved? → Mark executed → E-mail.

**Сказать:** «Ссылки подписаны HMAC-токеном: нельзя одобрить чужое действие, подменив номер».

## 6. Новая игра (1 мин) — «работает и для того, чего нет в базе»
*Прогноз и действия → Новая игра:* Nintendo Wii, Racing / Driving, сиквел, **4 часа** сюжета, 1 игрок, издатель THQ.
- Высокий риск; среди мер — «Расширить контент» и «Мультиплеер»: их эффект посчитан **моделью**, а не придуман.

## 7. Мониторинг и качество агента (1 мин)
- Журнал прогнозов, **data drift (PSI)** по признакам — сигнал к переобучению.
  PSI считается от 20 прогнозов *новых* игр (форма «Новая игра»); до этого страница честно пишет «недостаточно данных».
  Хотите показать график — заранее сделайте ~20 прогнозов через форму.
- Оценка агента (`reports/agent_eval_*.json`): насколько решения LLM совпадают с модулем решений, частота guardrail,
  время ответа на GPU.

## Если что-то пошло не так
| Симптом | Что делать |
|---|---|
| «Rule-based агент (LLM недоступна)» | `docker compose restart llm`, подождать 20 с. Агент всё равно отработает без LLM — это штатный fallback |
| Письма не пришли | Mailpit http://localhost:8025; в n8n → Executions — красная нода покажет ошибку SMTP |
| Строк нет в таблице | Таблица открыта сервисному аккаунту на редактирование? Ошибка Sheets не останавливает процесс |
| Медленно (> 40 с) | Проверить `docker compose logs llm \| findstr CUDA` — модель должна быть на GPU |

## Вопросы, которые могут задать
- **Почему PR-AUC, а не accuracy?** Провалов 18–23 %; accuracy 80 % даёт «всегда хорошо», а нам важно находить провалы.
- **Почему качество «всего» 0.39?** ~900 игр и только признаки, известные *до* релиза. После удаления утечки метрики
  честно упали — завышенная модель была бы бесполезна в реальности.
- **Как считается эффект мер?** Продуктовые меры (контент, мультиплеер, платформа) — what-if через модель;
  процессные (QA, плейтест, PR, перенос) — явные экспертные допущения, это вынесено в ограничения.
- **Зачем LLM, если есть модуль решений?** LLM выбирает инструменты, объясняет и может учесть контекст; модуль решений —
  страховка и эталон. Все цифры в отчёте берутся из инструментов, LLM их не выдумывает.
- **Что если LLM ошибётся?** Guardrails: только коды из каталога, обязательная фиксация плана, правило низкого риска,
  дорогие меры — только через человека.
