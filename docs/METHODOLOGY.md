## 2. Методология выборки
* **Единица наблюдения** — игра на конкретной платформе; в обучение идут только игры с оценкой критиков.
* **Разбиение по времени** (а не случайное): обучение — релизы **до 2012** (7 149 игр), тест — **2013–2016** (991 игра).
  Модель проверяется «на будущем», как будет работать в жизни; случайное разбиение завысило бы качество.
* **Кросс-валидация** — 5-fold *стратифицированная*: в каждом фолде та же доля провалов (≈25 %). На ней подбираются
  гиперпараметры и выбирается модель. **Тест в выборе не участвует** — только финальная проверка.
* **Дисбаланс классов**: провалов 25 % в обучении и 14 % в тесте → веса классов (`class_weight`, `scale_pos_weight`),
  метрика PR-AUC, порог подбирается отдельно.
* **Финальная модель** после выбора переобучается на **всех** годах (максимум данных для работы). Поэтому
  честное качество — это цифры теста, посчитанные **до** переобучения; игры из базы рабочая модель уже «видела».
* **Защита от утечки**: в признаках только то, что известно до релиза (продажи, оценки пользователей, число отзывов —
  исключены); история издателя и студии считается только по прошлым годам. Закреплено тестами.

## 3. Сезонные компоненты
Месяца релиза в данных нет (только год), поэтому «праздничный сезон» посчитать нельзя — и мы так и говорим.
Цикл индустрии игр — это **поколения консолей**: ранние игры, расцвет, конец поколения. Признаки:
* `console_age` — сколько лет платформе на момент выхода игры (жизненный цикл, 6-й по важности SHAP);
* `release_year` — долгосрочный тренд (2-й по важности: в 2013–2016 провалов меньше — 9–18 % против 25–31 %
  в 2006–2010, рынок «повзрослел»).

## 4. Модели: суть в двух словах (общее понимание)
| Семейство | Модель | Суть |
|---|---|---|
| — | Baseline | всегда отвечает «доля провалов»; нижняя планка |
| линейная | Логистическая регрессия | взвешенная сумма признаков → вероятность через сигмоиду; просто и объяснимо |
| по соседям | K-Nearest Neighbors | смотрит на K самых похожих игр и берёт их долю провалов |
| вероятностная | Naive Bayes | теорема Байеса при допущении, что признаки независимы (здесь неверно → слабая) |
| ядерная | SVM (RBF) | строит разделяющую границу в «искривлённом» пространстве признаков |
| дерево | Decision Tree | цепочка вопросов «если…то»; наглядно, но переобучается |
| бэггинг | Random Forest, Extra Trees | сотни деревьев на случайных подвыборках, голосуют; устойчиво |
| бустинг | AdaBoost, Gradient Boosting, LightGBM, XGBoost | деревья строятся по очереди, каждое исправляет ошибки предыдущих |
| регрессия | Linear/Ridge/Lasso, KNN, дерево, лес, бустинг | то же, но предсказывают число (оценку 0–100) |

## 5. Результаты: 3 этапа
PR-AUC (чем выше, тем лучше; baseline = доля провалов). CV — 5-fold на обучении, тест — 2013–2016.

|---|---|---|---|---|

| 1 | Naive Bayes | 0.379 | 0.204 | 0.591 |
| 1 | Decision Tree | 0.441 | 0.222 | 0.660 |
| 1 | AdaBoost | 0.460 | 0.269 | 0.711 |
| 1 | Logistic Regression | 0.467 | 0.311 | 0.714 |
| 1 | K-Nearest Neighbors | 0.470 | 0.322 | 0.729 |
| 1 | SVM (RBF) | 0.503 | 0.342 | 0.760 |
| 1 | Gradient Boosting | 0.518 | 0.276 | 0.720 |
| 1 | Extra Trees | 0.522 | 0.287 | 0.724 |
| 1 | Random Forest | 0.539 | 0.306 | 0.738 |
| 1 | XGBoost | 0.540 | 0.316 | 0.746 |
| 1 | LightGBM | 0.550 | 0.291 | 0.743 |
| 2 | Random Forest (tuned) | 0.563 | 0.309 | 0.740 |
| 2 | XGBoost (tuned) | 0.564 | 0.307 | 0.733 |
| **2** | **LightGBM (tuned) — выбрана** | **0.574** | 0.294 | 0.737 |
| 3 | Голосование большинством (3 из 5) | 0.488 | 0.259 | 0.696 |
| 3 | Усреднение вероятностей (soft voting) | 0.574 | 0.311 | 0.736 |
| 3 | Стекинг (логистическая мета-модель) | 0.486 | 0.281 | 0.712 |

**Выводы:**
* Все модели в 2+ раза лучше baseline. Лучшие — ансамбли деревьев (бэггинг/бустинг), как и у PyCaret.
* **Подбор гиперпараметров** дал прирост: LightGBM 0.550 → 0.574.
* **Голосование «3 из 5»** проверено и *проиграло* (0.488): при голосовании теряется уверенность моделей — остаются
  только 6 уровней (0–5 голосов), ранжирование грубое. **Усреднение вероятностей** сохраняет уверенность и
  догнало лучшую модель (0.574). Выбрана одиночная LightGBM — при равенстве проще, быстрее и точно объясняется SHAP.
* Рабочая модель: калибровка Platt + порог по **F2** (полнота важнее: пропущенный провал стоит сотни k$, лишняя
  тревога — максимум дешёвый плейтест). На тесте: **находит 68 % провалов**, точность 25 %, PR-AUC 0.294.

**AutoML (PyCaret)** на тех же данных и том же тесте: лидер — Random Forest (CV PR-AUC 0.573), стекинг трёх лучших —
тест 0.312; `tune_model` улучшения не нашёл и оставил исходную модель. Это **независимо подтверждает** ручной выбор.

**Регрессия** (прогноз самой оценки): лучшее — усреднение трёх лучших регрессоров, MAE **8.3 балла** (CV), R² 0.42;
линейная регрессия — MAE 9.5, R² 0.27. Ранжирует провалы так же хорошо, как классификатор (CV PR-AUC 0.567 против 0.574),
но правило «прогноз < 60 → провал» ловит лишь ~20 %: прогнозы регрессии «сжимаются» к среднему (≈70).
Поэтому решение «провал/нет» принимает классификатор с подобранным порогом, регрессия — второе мнение.

## 6. Метрики — суть
Матрица ошибок: **TP** — провал предсказан и случился; **FP** — ложная тревога; **FN** — пропущенный провал; **TN** — верно «не провал».

| Метрика | Формула / смысл | Зачем здесь |
|---|---|---|
| Accuracy | доля верных ответов | **обманчива**: baseline «никогда не провал» даёт 86 % на тесте, лучшая модель — 80 % |
| Precision (точность) | TP / (TP+FP) — из всех тревог сколько настоящих | стоимость ложных тревог |
| Recall (полнота) | TP / (TP+FN) — какую долю провалов нашли | главная для бизнеса: пропуск дорог |
| F1 / F2 | гармоническое среднее P и R; F2 вдвое сильнее ценит recall | выбор порога |
| ROC-AUC | вероятность, что случайный провал получит риск выше случайного хита; 0.5 = монетка | общее качество ранжирования |
| **PR-AUC** | площадь под кривой precision–recall; baseline = доля провалов | **главная**: честна при редком классе |
| Brier | средний квадрат ошибки вероятности | качество калибровки (вероятности нужны для расчёта денег) |
| MAE / RMSE | средняя ошибка в баллах; RMSE сильнее штрафует большие промахи | регрессия |
| R² | доля разброса оценок, объяснённая моделью (0 = как среднее, 1 = идеально) | регрессия |

## 7. AI agent vs Agentic AI
* **AI agent** — одна LLM, которая сама решает, какие **инструменты** вызвать, чтобы выполнить задачу, и действует
  (в нашей системе: 7 инструментов — прогноз, SHAP, похожие игры, издатель, оценка мер, база знаний, отправка плана).
* **Agentic AI** — **система**, в которой автономность распределена: агент + детерминированные компоненты +
  оркестрация + память + человек в контуре; она сама ведёт процесс от события до результата.
* Наша система — именно agentic: событие (новые игры по расписанию, RPA) → ML-прогноз → агент с инструментами и RAG →
  защитные правила (guardrails) → n8n запускает действия → человек утверждает дорогие → решения пишутся в журнал и
  становятся новой «памятью» базы знаний.

## 8. RAG (retrieval-augmented generation)
Перед решением агент вызывает `search_knowledge_base`: поиск по базе знаний (TF-IDF по символьным n-граммам — работает
на русском, румынском и английском без внешних моделей). База знаний:
* `docs/kb/measures_playbook.md` — когда какая мера помогает и чем рискует;
* `docs/kb/company_policy.md` — правила согласования, лимиты, лицензионные игры, сиквелы;
* `docs/kb/data_insights.md` — **факты, посчитанные из данных** (доля провалов по жанрам, платформам, длине, сиквелам);
  пересчитывается автоматически при каждом обновлении данных;
* журнал прошлых решений менеджера из БД — база знаний растёт с каждым решением.
Найденные фрагменты попадают в отчёт агента («Из базы знаний (RAG)»), LLM опирается на них.

## 9. RPA: автоматическое обновление данных
Ежедневно в 08:00 n8n запускает сценарий (или вручную: webhook `nrg-refresh` / кнопка на странице «Мониторинг»):
1. новые игры приходят CSV-файлом в `data/incoming/` (пример — `docs/examples/incoming_example.csv`);
2. каждая строка проверяется (обязательные поля, известная платформа, диапазоны) — ошибки попадают в отчёт;
3. новые игры добавляются в БД, дубли пропускаются;
4. для ещё не вышедших игр (без оценки) сразу считается риск;
5. пересчитываются факты базы знаний (RAG), строка пишется в журнал и Google Sheets;
6. если есть игры с высоким риском — команде уходит письмо со списком.
